- **TOPIC**: Docker Compose Architecture: Defining Distributed Systems Declaratively
- **GOAL**: Explain declarative multi-container orchestration for local development and staging environments.

### Hook:
> Running 5 separate `docker run` commands with 12 flags each is an operational disaster waiting to happen.  
> Here is how Docker Compose translates manual CLI commands into a single, declarative infrastructure spec.

### Full Post:
When an application grows from a single binary into a multi-tier microservice architecture (Frontend + API + Redis Cache + Postgres Database), managing containers via CLI scripts becomes unmaintainable.

**Docker Compose** is Docker's declarative orchestration specification for multi-container environments.

Instead of imperatively running commands:
`docker run -d --name db -v pgdata:/var/lib/postgresql/data -p 5432:5432 postgres`

You define the desired state in a single `docker-compose.yml` file:
```yaml
services:
  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    ports:
      - "8080:8080"
    environment:
      - DB_HOST=postgres
      - REDIS_HOST=redis
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - app-tier

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app_prod
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    volumes:
      - db_data:/var/lib/postgresql/data
    networks:
      - app-tier

volumes:
  db_data:

networks:
  app-tier:
```

What Docker Compose does automatically:
1. Provisions a dedicated, isolated user-defined bridge network for the stack.
2. Configures DNS resolution so services can communicate using their service names (`postgres`, `redis`).
3. Manages persistent volume lifecycles independently of container restarts.
4. Boots, stops, and scales the entire distributed system with a single command: `docker compose up -d`.

It is the stepping stone between single-host containerization and Kubernetes cluster orchestration.

- **TOPIC**: Container Healthchecks in Docker: `interval`, `timeout`, and `retries`
- **GOAL**: Teach engineers how to detect deadlocked or hung containers automatically.

### Hook:
> Just because a container is running doesn't mean your application is healthy.  
> If an API deadlocks or enters an infinite loop, Docker still reports `Up (healthy)`—unless you write a real healthcheck.

### Full Post:
By default, Docker monitors only ONE metric to determine if a container is running:
**Is PID 1 still alive?**

If your Node/Python/Java process deadlocks, loses its database connection pool, or runs out of worker threads, PID 1 is technically still active.
Docker happily keeps the container running, while users experience `504 Gateway Timeouts`.

Enter the **Docker HEALTHCHECK**:
A healthcheck instructs Docker to run a command inside the container periodically to verify that the application is actually serving traffic.

The 4 Healthcheck Parameters:
1. `test`: The probe command (e.g., `curl -f http://localhost:8080/health || exit 1`).
2. `interval`: How often to execute the check (default: `30s`).
3. `timeout`: How long to wait before declaring a check failed (default: `30s`).
4. `retries`: How many consecutive failures before marking the container `unhealthy` (default: `3`).
5. `start_period`: Grace period for slow application boots before failures count against the retry limit (e.g., `40s` for Java apps).

How to define it in Docker Compose:
```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres || exit 1"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 10s
```

Why this is critical:
When a container transitions from `starting` to `healthy`, downstream services know it is safe to connect, and load balancers know it is safe to route traffic.

If your container lacks a healthcheck, you are flying blind.

- **TOPIC**: The `depends_on` Trap in Docker Compose: Why `service_healthy` is Mandatory
- **GOAL**: Prevent race conditions where backend services crash because the database hasn't finished booting.

### Hook:
> You add `depends_on: [postgres]` to your API service in Docker Compose.  
> You run `docker compose up`, and your API crashes immediately with `ECONNREFUSED`.  
> Here is why `depends_on` alone doesn't do what you think it does.

### Full Post:
This is one of the most common gotchas in container orchestration.

You expect `depends_on: - postgres` to mean:
*"Wait until Postgres is fully booted and ready to accept SQL queries before starting my API."*

In reality, Docker Compose interprets `depends_on` as:
*"Start the Postgres container process, and the millisecond that PID starts, IMMEDIATELY start the API container."*

The Problem (The Race Condition):
Postgres takes 5 to 10 seconds to initialize its data directory, load configuration files, and bind to port 5432.
Meanwhile, your fast Node/Go API boots in 400 milliseconds, attempts to connect to port 5432, finds no listening socket, throws an uncaught database connection error, and crashes!

The Solution: `condition: service_healthy`
You must combine `depends_on` with a Docker healthcheck:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

  api:
    build: ./api
    depends_on:
      postgres:
        condition: service_healthy # The Magic Line!
```

Now, Docker Compose will deliberately pause the API service. It waits until Postgres passes its `pg_isready` healthcheck probe, and ONLY THEN boots your API.

Zero race conditions. Zero crashed containers. 100% deterministic startup.

- **TOPIC**: Secrets & Environment Variables in Docker Compose: `.env` vs `environment:` vs `secrets:`
- **GOAL**: Explain secure secret handling in multi-container stacks without baking keys into git.

### Hook:
> Storing database passwords in your `docker-compose.yml` file is the fastest way to leak production credentials into GitHub.  
> Here is the right way to manage environments, variables, and secrets in Docker Compose.

### Full Post:
Docker Compose provides 3 different ways to inject configuration data. Using them incorrectly exposes secrets to developers, logs, and Git histories.

Here is the proper security hierarchy:

1. The `.env` File (Interpolation Only):
• Purpose: Sets variables for Compose YAML *interpolation* (e.g., `image: myapp:${TAG}`).
• Docker Compose automatically reads a local `.env` file in the same directory.
• CRITICAL: Never commit `.env` to Git! Add it to `.gitignore` and maintain a sanitized `.env.example` in the repository.

2. The `environment:` Array (Non-Sensitive Configs Only):
• Best for: Non-secret operational settings (e.g., `PORT=8080`, `LOG_LEVEL=debug`, `NODE_ENV=production`).
• Avoid for passwords, because anyone who runs `docker inspect <container>` can see these variables in plain text!

3. Docker Compose Secrets (`secrets:` - The Gold Standard):
Instead of injecting passwords as environment variables, mount them as in-memory files:

```yaml
services:
  db:
    image: postgres:16-alpine
    secrets:
      - db_password
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

Why Secrets are Superior:
• The secret is mounted into an in-memory virtual filesystem at `/run/secrets/db_password`.
• It is NEVER stored in image layers.
• It is NEVER exposed in `docker inspect` output or process tables (`ps aux`).
• When the container stops, the secret evaporates from RAM.

Configure non-sensitive settings in `environment:` and sensitive credentials in `secrets:`.

- **TOPIC**: Docker Compose Profiles: Managing Dev, Test, and Debugging Stacks from One File
- **GOAL**: Teach engineers how to avoid maintaining multiple fragmented compose files.

### Hook:
> Maintaining `docker-compose.dev.yml`, `docker-compose.test.yml`, and `docker-compose.prod.yml` creates copy-paste drift and headaches.  
> Here is how Docker Compose **Profiles** let you manage your entire multi-environment lifecycle from a single file.

### Full Post:
In a real engineering workflow, you don't always want to start every service.
• When writing code: You only need the API and Database.
• When debugging: You want pgAdmin and Redis Commander.
• When running CI: You want the End-to-End Cypress test runner.

Before Compose Profiles, engineers maintained 4 different YAML files that inevitably fell out of sync.

With **Profiles**, you assign services to named logical groups directly in your main `docker-compose.yml`:

```yaml
services:
  api:
    image: my-api:latest
    ports: ["8080:8080"]

  postgres:
    image: postgres:16-alpine

  # Debugging tools (Only boot when requested)
  pgadmin:
    image: dpage/pgadmin4
    profiles: ["debug"]

  # Automated test runner (Only boot during CI)
  e2e-tests:
    build: ./tests
    profiles: ["test"]
```

How to use it:
1. Standard Development (Starts ONLY api and postgres):
`docker compose up`

2. Need database UI tools for debugging?
`docker compose --profile debug up`
(Starts api, postgres, AND pgadmin!)

3. Running automated test suite in CI?
`docker compose --profile test run e2e-tests`

One clean source of truth. Zero duplicated YAML. Modular developer environments.

Stop maintaining 5 different Docker Compose files! How Docker Compose `profiles:` allow you to toggle development, testing, and debugging stacks from a single configuration file.

- **TOPIC**: Horizontal Scaling with Docker Compose: `--scale` + Nginx Reverse Proxy
- **GOAL**: Teach local horizontal scaling and load balancing before stepping into Kubernetes.

### Hook:
> What happens when your single API container can’t handle incoming traffic?  
> With 1 command, you can scale to 5 container replicas and load balance traffic across them with Nginx.

### Full Post:
Before jumping into the complexity of Kubernetes Pod autoscaling, you can simulate and test horizontal scaling directly on your laptop using Docker Compose.

The Architecture:
• 1 Nginx Reverse Proxy container (Public port 80).
• N identical stateless API backend container replicas.
• 1 Shared Postgres database.

How to configure Nginx to load balance across Compose replicas:
In your `nginx.conf`:
```nginx
upstream api_servers {
    server api:8080;
}

server {
    listen 80;
    location / {
        proxy_pass http://api_servers;
    }
}
```

The Docker Magic:
Because Docker's embedded DNS server (`127.0.0.11`) automatically returns all IP addresses associated with the service name `api` in round-robin order, Nginx automatically distributes traffic evenly across all running replicas!

To scale the API to 4 replicas:
`docker compose up -d --scale api=4`

Now, when you send 100 requests to `http://localhost:80`:
• Request 1 -> hits Replica 1
• Request 2 -> hits Replica 2
• Request 3 -> hits Replica 3
• Request 4 -> hits Replica 4

If one replica crashes, Nginx routes around it, and Docker brings up a replacement.

Stateless microservice scaling in action.
