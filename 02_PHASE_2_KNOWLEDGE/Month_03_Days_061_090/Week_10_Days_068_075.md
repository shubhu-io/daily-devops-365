- **GOAL**: Explain how modern cloud virtualization works without hypervisor tax.

### Hook:
> In traditional virtualization, up to 30% of a server's CPU and memory is consumed just running the hypervisor.  
> AWS eliminated that hypervisor tax completely. Meet the AWS Nitro System.

### Full Post:
Amazon Elastic Compute Cloud (EC2) powers millions of applications worldwide. But modern EC2 instances are nothing like the legacy VMs of 2010.

Historically, hypervisors (like Xen) had to manage storage I/O, network packet switching, and security isolation directly on the main CPU.

In 2017, AWS revolutionized cloud hardware with the **AWS Nitro System**:
Instead of using host CPU cycles for hypervisor management, AWS offloaded all non-compute tasks to **dedicated custom ASIC hardware chips (Nitro Cards)**:
• Nitro Card for VPC: Manages network encryption and packet routing in dedicated silicon (achieving up to 100Gbps networking).
• Nitro Card for EBS: Offloads NVMe storage controller processing.
• Nitro Security Chip: Continuously monitors hardware firmware, enforcing a cryptographic root of trust.
• Nitro Hypervisor: A featherweight, bare-metal hypervisor that simply partitions CPU cores and RAM.

The Result: **Almost 100% of the physical server's CPU and RAM is dedicated to YOUR workload!**

The EC2 Instance Family Decoder Ring:
• `t4g`, `m6i`, `c7g`, `r6i`... What do the letters mean?
  - First Letter = Purpose:
    • `T` / `M` = General Purpose (Balanced CPU & RAM)
    • `C` = Compute Optimized (CPU-heavy workloads, batch processing)
    • `R` = Memory Optimized (Databases, Redis in-memory caches)
  - Number = Generation (Higher is newer, faster, cheaper)
  - Suffix = Processor Type:
    • `g` = AWS Graviton (ARM-based, 40% better price-to-performance!)
    • `i` = Intel Xeon
    • `a` = AMD EPYC

Pick ARM Graviton (`g`) whenever possible to instantly slash your cloud bill.

### Hook:
> Two companies run the exact same 100 EC2 instances on AWS.  
> Company A pays $10,000/month. Company B pays $2,200/month.  
> The difference is understanding AWS purchasing models.

### Full Post:
Running everything on default "On-Demand" pricing is the fastest way to burn through your company's cloud budget.

AWS offers 4 distinct compute purchasing models:

1. On-Demand (Maximum Flexibility, Maximum Cost):
• Pay by the second with zero upfront commitment.
• When to use: Short-term spikes, experimental workloads, initial development.
• Cost Discount: **0% (Full Price)**.

2. Compute Savings Plans & Reserved Instances (Commitment Discounts):
• You commit to a consistent compute usage (e.g., $10/hour) for a 1-year or 3-year term.
• Compute Savings Plans automatically apply across EC2, AWS Fargate, and Lambda regardless of instance family, region, or OS!
• Cost Discount: **Up to 66% to 72% off On-Demand rates**.
• When to use: Predictable baseline production workloads (core databases, steady-state API pods).

3. Spot Instances (The 90% Discount Superpower):
• AWS has massive pools of spare, unused compute capacity in their data centers.
• They sell this spare capacity at up to a **90% discount**!
• The Catch: If AWS needs the capacity back for On-Demand customers, they give you a **2-minute warning notification**, and terminate the instance!
• When to use: Stateless workloads, batch processing, CI/CD runners, Kubernetes worker nodes running behind an Auto Scaling Group with Spot diversification.

The Production Gold-Standard Architecture:
Use **Savings Plans** for your steady-state baseline (the 40% of compute that runs 24/7/365).  
Use **Spot Instances** inside an Auto Scaling Group for dynamic traffic spikes (the remaining 60%).

Cost drops by 70%+ with zero impact on user availability.

- **GOAL**: Explain self-healing compute fleets and dynamic scaling policies.

### Hook:
> If an EC2 instance crashes at 3:00 AM on Saturday, do you want a pager waking you up?  
> Or do you want an Auto Scaling Group that replaces it automatically in 90 seconds?

### Full Post:
Even if your application doesn't experience fluctuating traffic, you should NEVER run a production application on a standalone EC2 instance.

Always run it inside an **AWS Auto Scaling Group (ASG)**.

An Auto Scaling Group provides two critical capabilities:

1. Self-Healing Fleet Management:
Set `Min: 2`, `Desired: 2`, `Max: 6` across multiple Availability Zones.
• If a server crashes, fails an EC2 status check, or fails an Application Load Balancer healthcheck probe:
• The ASG immediately terminates the unhealthy instance.
• It automatically provisions an identical, healthy replacement instance from a **Launch Template**.
• You achieve automated self-healing without human intervention!

2. Dynamic Scaling Policies (Elasticity):
Scale compute capacity automatically based on real-time application load:
• Target Tracking Scaling: Set a target metric (e.g., "Keep average fleet CPU utilization at 60%"). AWS automatically scales the instance count up or down to maintain that target!
• Step Scaling / Simple Scaling: "If CPU > 80% for 3 minutes, add 2 instances. If CPU < 30%, remove 1 instance."
• Predictive Scaling: Uses machine learning to forecast daily traffic curves and pre-provisions instances *before* the morning spike hits!

Best Practice:
Always pair Auto Scaling Groups with a **Launch Template** (versioned, supports Spot/On-Demand mixing, supports multiple instance types) rather than legacy Launch Configurations.

- **TOPIC**: Amazon EBS (Elastic Block Store) Demystified: GP3 vs IO2 and IOPS Math
- **GOAL**: Explain block storage, IOPS, throughput, and how to avoid overpaying for disk performance.

### Hook:
> Why is your cloud database running slow even though CPU and Memory are at 20%?  
> Check your disk IOPS. Here is how AWS Elastic Block Store (EBS) performance actually works.

### Full Post:
Amazon Elastic Block Store (EBS) is network-attached block storage for EC2 instances (think of it as a high-speed virtual SSD plugged in over an ultra-fast private network cable).

Understanding the difference between **IOPS** and **Throughput** dictates your database performance:
• **IOPS (Input/Output Operations Per Second)**: How many small read/write operations the disk can handle per second (critical for transactional databases like PostgreSQL/MySQL).
• **Throughput (MB/s)**: How much raw volume of data the disk can stream per second (critical for large file transfers, video processing, and log analytics).

The EBS Volume Family Breakdown:

1. General Purpose SSD: GP2 vs GP3 (The Easy Cost Win):
• **GP2 (Legacy)**: Tied IOPS directly to disk size! To get 3,000 IOPS, you had to provision a 1,000 GB disk, even if you only needed 50 GB of data.
• **GP3 (Modern Standard)**: Decouples storage from performance!
  - Baseline: Delivers 3,000 IOPS and 125 MB/s throughput included for FREE, regardless of volume size.
  - Scale independently: Need 10,000 IOPS on a 100 GB disk? Simply dial up IOPS without provisioning unnecessary storage.
  - **GP3 is 20% cheaper than GP2!** If you have any GP2 volumes today, convert them to GP3 with zero downtime.

2. Provisioned IOPS SSD: IO1 vs IO2:
• Designed for mission-critical, high-throughput, low-latency enterprise databases.
• Up to 64,000 IOPS (IO1) or 256,000 IOPS (IO2 Block Express).
• Sub-millisecond latency and 99.999% volume durability.
• Expensive—use only when GP3 baseline limits are exhausted.

Storage Rule:
Convert every GP2 volume to GP3 immediately. Monitor CloudWatch `VolumeQueueLength` and `VolumeThroughputPercentage` to detect disk bottlenecks before users do.

- **TOPIC**: EBS Snapshots Under the Hood: Incremental Backups & Cross-Region Disaster Recovery
- **GOAL**: Explain point-in-time recovery and snapshot mechanics for stateful cloud systems.

### Hook:
> If you take a 100 GB EBS snapshot every night for 30 days, do you pay for 3,000 GB of storage?  
> No. Here is how EBS snapshots use block-level incremental tracking to save 90% of your backup costs.

### Full Post:
Backing up stateful databases and cloud block storage is critical for disaster recovery (RPO - Recovery Point Objective).

EBS Snapshots are point-in-time backups stored durability inside Amazon S3:

How Block-Level Incremental Backups Work:
1. Snapshot 1 (Initial Full Baseline):
Takes your 100 GB volume and compresses all written blocks into S3. If only 30 GB of data is written, it stores 30 GB.

2. Snapshot 2 (Incremental Change):
24 hours later, your database modified 2 GB of data.
AWS tracks modified blocks at the block-device level. Snapshot 2 **ONLY uploads the 2 GB of changed blocks**! It links back to Snapshot 1 for the unchanged blocks.

3. What happens when you delete Snapshot 1?
Many engineers fear deleting Snapshot 1 will corrupt subsequent backups.
It won't! AWS automatically consolidates blocks: any block needed by Snapshot 2 is retained. Only blocks unique to Snapshot 1 are permanently deleted.

Automating Disaster Recovery (AWS Backup & DLM):
• Use **Amazon Data Lifecycle Manager (DLM)** to automate snapshot retention policies (e.g., keep 7 daily, 4 weekly, 12 monthly snapshots).
• Use **Cross-Region Snapshot Copy**: Automatically replicate snapshots from `us-east-1` to `eu-west-1`. If an entire AWS region experiences a catastrophic outage, you can restore your volume in a secondary region in minutes.

Fast Snapshot Restore (FSR):
Eliminate the "lazy loading" penalty! Standard restored EBS volumes pull blocks from S3 on first read (causing initial I/O latency). Enabling FSR pre-warms blocks for instant full-speed performance.

### Hook:
> What does "11 Nines of Durability" (99.999999999%) actually mean?  
> If you store 10,000,000 files in Amazon S3, you can expect to lose a single file once every 10,000 years.

### Full Post:
Amazon Simple Storage Service (S3) is an **Object Storage** system (files are stored with unique keys, metadata, and data payloads via REST APIs, rather than hierarchical file trees).

How AWS Delivers 11 Nines of Durability:
When you upload a file to S3 Standard, AWS automatically replicates that object across a minimum of **three geographically separated Availability Zones**. Even if an entire data center is completely destroyed, your data remains intact and accessible.

The S3 Storage Tier Hierarchy (Slashing Storage Bills):
Not all data needs instant millisecond retrieval. Using S3 Lifecycle Rules, you can automatically transition objects across tiers over time:

1. S3 Standard:
• Frequent access, millisecond latency.
• Use case: Active website assets, dynamic user uploads. (~$0.023/GB).

2. S3 Standard-Infrequent Access (Standard-IA):
• Millisecond latency, but 50% cheaper storage cost! (~$0.0125/GB).
• Catch: Small retrieval fee per GB.
• Use case: Backups older than 30 days, historical logs.

3. S3 Glacier Flexible Recovery:
• Secure archive storage (~$0.0036/GB - 85% cheaper than Standard!).
• Retrieval time: 1–5 minutes (Expedited) or 3–5 hours (Standard).

4. S3 Glacier Deep Archive:
• The lowest cost storage in the cloud (~$0.00099/GB - 95% cheaper!).
• Retrieval time: 12 hours.
• Use case: Long-term compliance archives (HIPAA, tax records, audit logs) retained for 7–10 years.

5. S3 Intelligent-Tiering:
• Automatically monitors access patterns and shifts objects between Frequent, Infrequent, and Archive tiers without any retrieval fees or operational overhead!

Automate your lifecycle policies: Day 1 (Standard) -> Day 30 (Standard-IA) -> Day 90 (Glacier) -> Day 365 (Deep Archive).

- **TOPIC**: S3 Security & Static Hosting: Origin Access Control (OAC) with CloudFront
- **GOAL**: Explain how to host static frontends securely without making S3 buckets public.

### Hook:
> The old way to host a static website on AWS: Make the S3 bucket public and enable "Static Website Hosting".  
> The secure modern way: Keep the bucket completely private and use CloudFront with Origin Access Control (OAC).

### Full Post:
Making an S3 bucket publicly readable (`Block Public Access: Off`) is an operational security hazard.

Anyone on the internet can scan for the S3 bucket endpoint, bypass your CDN, hotlink your images, and trigger massive bandwidth egress bills directly on your account.

The Modern Production Standard: **Private S3 + CloudFront CDN + Origin Access Control (OAC)**.

Here is the secure architecture:

1. Keep S3 Completely Private:
• Enable **Block All Public Access** on the S3 bucket.
• Disable S3 "Static Website Hosting" mode!
• The S3 bucket has zero public endpoints and is unreachable from the open internet.

2. CloudFront Edge Distribution:
• Set up an Amazon CloudFront distribution pointing to the S3 bucket as its origin.
• CloudFront terminates HTTPS at the edge using free SSL certificates from AWS Certificate Manager (ACM).
• Provides global edge caching across 600+ PoPs and DDoS mitigation via AWS Shield Standard.

3. Origin Access Control (OAC):
• Replaces legacy Origin Access Identity (OAI).
• CloudFront cryptographically signs every request sent to S3 using AWS SigV4.
• In your S3 Bucket Policy, you add a policy that allows ONLY the specific CloudFront distribution ARN to execute `s3:GetObject`:

```json
{
  "Version": "2012-10-17",
  "Statement": {
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": {
      "Service": "cloudfront.amazonaws.com"
    },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-frontend-app/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/EDFDVBD632BHDS5"
      }
    }
  }
}
```

Now, users can only access your frontend via your custom domain through CloudFront. The S3 bucket remains 100% private and protected.
