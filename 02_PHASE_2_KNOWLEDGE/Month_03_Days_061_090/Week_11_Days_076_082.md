- **TOPIC**: Amazon VPC Architecture from Scratch: Public vs Private Subnets & Isolation
- **GOAL**: Teach engineers how to design isolated network topologies in AWS.

### Hook:
> Most tutorials deploy databases into a default AWS VPC with a public IP address.  
> That is how databases get scanned by bots and compromised. Here is how a real production VPC is architected.

### Full Post:
An **Amazon Virtual Private Cloud (VPC)** is your logically isolated, private software-defined data center inside AWS.

When you create a production VPC, you divide your IP space into distinct **Subnets** with strict traffic isolation:

The 3-Tier Production Subnet Architecture:

1. Public Subnet (The Demilitarized Zone - DMZ):
• What lives here: Internet-facing Application Load Balancers (ALB) and NAT Gateways.
• Routing: Associated with a Route Table that has a route to an **Internet Gateway (IGW)** (`0.0.0.0/0 -> igw-xxxx`).
• Rule: NEVER place databases or core backend application containers here!

2. Private Application Subnet (The Compute Tier):
• What lives here: EC2 instances, Kubernetes worker nodes (EKS), and ECS container tasks.
• Routing: No direct route to the Internet Gateway. Instances have private IPs only (`10.0.10.0/24`).
• Outbound Access: Can talk to the outside internet (to download security updates or call external Stripe APIs) ONLY via a **NAT Gateway** located in the Public Subnet!
• Inbound Access: Cannot be reached directly from the internet. All incoming user traffic MUST enter through the Application Load Balancer in the Public Subnet!

3. Isolated Database Subnet (The Data Tier):
• What lives here: PostgreSQL/MySQL (RDS), Redis (ElastiCache).
• Routing: ZERO internet access. No route to the Internet Gateway AND no route to the NAT Gateway!
• Inbound Access: Whitelisted to accept traffic ONLY from the Private Application Subnet on port 5432/3306.

Even if an attacker attempts to scan your database, it is physically impossible to route packets to it from the public internet.

Defense in depth starts at the network boundary.

- **TOPIC**: Internet Gateways vs NAT Gateways (And the $3,000 NAT Gateway Bill Trap)
- **GOAL**: Explain outbound internet routing and how to avoid massive NAT data transfer fees.

### Hook:
> You spin up an AWS NAT Gateway to let private instances download updates.  
> Next month, your AWS bill has a $3,000 charge for "NAT Gateway Data Processing". Here is what happened and how to fix it.

### Full Post:
To connect a VPC to the internet, you use two different gateways with completely different purposes:

🌐 1. Internet Gateway (IGW):
• Fully managed, horizontally scaled, redundant software router provided by AWS.
• Handles **2-way communication** (Inbound AND Outbound) for instances in Public Subnets.
• Cost: **100% FREE!** You only pay standard AWS data egress fees.

🛡️ 2. NAT Gateway (Network Address Translation):
• Sits in a Public Subnet to allow instances in Private Subnets to make **Outbound-ONLY connections** to the internet (while blocking anyone on the internet from initiating inbound connections).
• Rewrites the private source IP to the NAT Gateway's Elastic Public IP.
• Cost: **NOT FREE!**
  - Hourly fee: ~$32.40/month per NAT Gateway.
  - Data Processing Fee: **$0.045 per GB!**

⚠️ The $3,000 NAT Gateway Trap:
If your private EC2 instances or Kubernetes pods backup 50 TB of data to an **Amazon S3 bucket**, where does the traffic go?
By default, S3 is a public AWS service. Your private instances route all 50 TB through the NAT Gateway!
`50,000 GB * $0.045/GB = $2,250 in unnecessary NAT Gateway fees!`

The Instant Fix: **VPC Gateway Endpoints**!
Create an **S3 VPC Gateway Endpoint**:
• Routes all S3 traffic directly across AWS's private internal network backbone, completely bypassing the NAT Gateway.
• Cost: **100% FREE!**
• The $2,250 bill drops to $0.00 instantly.

Audit your VPC route tables today. S3 and DynamoDB traffic should NEVER touch a NAT Gateway.

- **TOPIC**: AWS Route Tables Demystified: The Longest Prefix Match Rule
- **GOAL**: Explain how packets navigate VPC networks using route table rules.

### Hook:
> An EC2 instance sends a packet to `10.0.2.45`.  
> Its Route Table has 3 different target routes. How does the AWS virtual router decide which path the packet takes?  
> The answer is the "Longest Prefix Match" rule.

### Full Post:
Every subnet in your AWS VPC must be associated with a **Route Table**.

A Route Table is a set of rules (called routes) that determine where network traffic directed from your subnet is forwarded.

Here is an example production Route Table for a Private Subnet:

| Destination CIDR | Target | Purpose |
|---|---|---|
| `10.0.0.0/16` | `local` | Internal VPC traffic (Never leaves the VPC) |
| `10.0.2.0/24` | `pcx-12345` | Peered VPC connection to Analytics VPC |
| `pl-63a5400a` | `vpce-98765` | S3 Gateway Endpoint prefix list |
| `0.0.0.0/0` | `nat-0abcd` | The Default Gateway (All other internet traffic) |

The Core Routing Rule: **Longest Prefix Match (Most Specific Route Wins)**:
When a packet leaves an instance, AWS compares the destination IP against all routes in the table:
1. If the destination is `10.0.1.50`, it matches `10.0.0.0/16` (Prefix `/16`). It routes internally (`local`).
2. If the destination is `10.0.2.45`, it matches BOTH `10.0.0.0/16` AND `10.0.2.0/24`.
   Because `/24` has more network bits (it is more specific than `/16`), **the `/24` route wins!** The packet travels across the VPC Peering connection (`pcx-12345`).
3. If the destination is `54.239.28.85` (external web), it matches none of the specific routes. It falls back to the **Default Route (`0.0.0.0/0`)** and travels through the NAT Gateway.

Understanding the Longest Prefix Match prevents routing conflicts when configuring VPC Peering, Transit Gateways, and VPN tunnels.

- **TOPIC**: Security Groups vs Network ACLs (NACLs): Stateful vs Stateless Firewalls
- **GOAL**: Untangle the two layers of firewall defense inside an AWS VPC.

### Hook:
> You open port 443 in an AWS Security Group, and HTTPS requests work immediately.  
> You open port 443 in a Network ACL, and requests fail with a timeout. Why?  
> Because one is Stateful, and the other is Stateless.

### Full Post:
AWS VPC provides two distinct layers of virtual firewall defense. Confusing their mechanics is the #1 cause of broken network connections in AWS:

🛡️ 1. Security Groups (The Instance Firewall - Stateful):
• Operates at the **Instance / ENI level** (Virtual Network Interface).
• Evaluates traffic before it enters or leaves an EC2 instance or container.
• Support ONLY **Allow rules** (Zero Deny rules; anything not explicitly allowed is denied by default).
• **STATEFUL**: If you allow incoming traffic on port 443, the response traffic returning to the user is **automatically allowed back out**, regardless of outbound rules! The firewall tracks connection state in memory.

🏰 2. Network Access Control Lists (NACLs - The Subnet Firewall - Stateless):
• Operates at the **Subnet boundary**.
• Evaluates traffic crossing the subnet perimeter (affects all instances inside the subnet).
• Supports BOTH **Allow and Deny rules** (Evaluated in strict numerical order, e.g., Rule 100, Rule 200).
• **STATELESS**: It does NOT track connection state!
  - If you allow incoming traffic on port 443 in a NACL, you must ALSO explicitly configure an Outbound Rule allowing **Ephemeral Ports (ports 1024–65535)** for the response packets to return!
  - If you forget the outbound ephemeral rule, the return packets are dropped at the subnet boundary!

When to Use Which:
• Security Groups: Your daily workhorse. Use for granular application-level port control (e.g., allow port 5432 only from ALB security group).
• NACLs: Use as a blunt defensive shield. Block malicious IP subnets, or blacklist compromised CIDR blocks across an entire subnet with an explicit DENY rule.

- **GOAL**: Provide a clear decision framework for selecting Layer 7 vs Layer 4 load balancing.

### Hook:
> Should you use an Application Load Balancer (ALB) or a Network Load Balancer (NLB)?  
> Pick the wrong one, and you either cannot route by URL path, or your ingress controller bottlenecks under millions of requests per second.

### Full Post:
Amazon Elastic Load Balancing (ELB) distributes incoming application traffic across multiple targets (EC2 instances, containers, IP addresses).

Here is the architectural comparison between ALB and NLB:

🌐 Application Load Balancer (ALB) — The Smart Layer 7 Router:
• Operates at **Layer 7 (Application Layer)**: Inspects HTTP and HTTPS packet contents.
• Advanced Routing Superpowers:
  - Path-based routing: `company.com/api` -> routes to Backend Target Group; `company.com/static` -> routes to S3/CDN.
  - Host-based routing: `api.company.com` vs `app.company.com`.
  - HTTP header & query parameter routing.
  - Native OpenID Connect (OIDC) authentication (authenticate users via Okta/Google before reaching your app!).
• TLS Termination: Offloads SSL certificate decryption using AWS Certificate Manager.
• Throughput: Highly scalable, but scales up reactively over a few minutes during sudden spikes.

⚡ Network Load Balancer (NLB) — The Raw Layer 4 Speed Demon:
• Operates at **Layer 4 (Transport Layer)**: Inspects only IP addresses and TCP/UDP ports. Does not parse HTTP headers.
• Throughput Superpower: Capable of handling **tens of millions of requests per second** with ultra-low, sub-millisecond latency!
• Static IP Support: Assigns a fixed, static Elastic IP address per Availability Zone (vital for legacy clients that whitelist IPs in corporate firewalls).
• Preserves Client Source IP: Passes the client's raw IP directly to backend instances without needing `X-Forwarded-For` headers.

Decision Rule:
• Microservices, REST APIs, web apps needing path/host routing? -> **ALB**.
• Extreme throughput, UDP gaming/video, gRPC, or strict static IP requirements? -> **NLB**.

- **TOPIC**: AWS PrivateLink & VPC Endpoints: Keeping Traffic on the Private Cloud Backbone
- **GOAL**: Teach engineers how to access AWS services and SaaS APIs without public internet exposure.

### Hook:
> Why should your private microservice send traffic out over the public internet just to read a secret from AWS Secrets Manager?  
> It shouldn't. Meet AWS PrivateLink and VPC Interface Endpoints.

### Full Post:
By default, most AWS managed services (S3, Secrets Manager, ECR, CloudWatch, DynamoDB) have public REST API endpoints.

If an application in your Private Subnet needs to pull a Docker image from ECR or query Secrets Manager, its traffic normally travels out through your NAT Gateway, onto the public internet, and back into AWS.

This introduces two major liabilities:
1. Security Risk: Traffic traverses the public internet, requiring NAT gateways and public DNS resolution.
2. Compliance Violations: Many healthcare (HIPAA) and financial (PCI-DSS) regulations mandate that sensitive customer data must NEVER traverse the public internet.

The Solution: **AWS VPC Endpoints & PrivateLink**:
A VPC Endpoint brings the AWS service directly INSIDE your private VPC!

The 2 Types of VPC Endpoints:

1. Gateway Endpoints (Free):
• Available for **Amazon S3** and **DynamoDB**.
• Modifies your VPC Route Table to route traffic directly across AWS’s internal private network.
• Zero hourly cost, zero data processing fees!

2. Interface Endpoints (Powered by AWS PrivateLink):
• Available for virtually all other AWS services (ECR, Secrets Manager, SSM, KMS, CloudWatch) and third-party SaaS vendors (Datadog, Snowflake).
• Provisions an **Elastic Network Interface (ENI)** with a private IP address directly inside your private subnet!
• Your instances talk to the service's private IP (`10.0.1.182`) using AWS Private DNS.
• Zero internet routing. Zero NAT gateway dependency. 100% private.

Secure your private workloads: If an app in a private subnet needs AWS APIs, provision a VPC Endpoint.
